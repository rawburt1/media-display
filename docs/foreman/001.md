---
id: 001
title: Track restart-required per output type, additive to the global flag
date: 2026-07-25
---

## Decision — the choice, named, in one paragraph

Track restart-required state per output *type_name* (the same granularity
`ConfigStore.save_form`'s `outputs` payload already arrives in - one output
detail page saves one output type's instances at a time), not via a full
before/after value diff and not by upgrading `config.yaml` with new
persisted state. `ConfigStore.save_form`/`save_raw`/`restore_backup` each
gained a third return value, `changed_output_types: FrozenSet[str]`:
`save_form` returns exactly the output type_names that were actually
present in `OUTPUT_CONFIG_TYPES` and merged from the posted `outputs` dict;
`save_raw`/`restore_backup` (which can rewrite the whole file with no
per-field provenance) conservatively return *every* registered output
type_name, mirroring their existing "assume a restart might be needed"
reasoning. `ConfigUiOutput` accumulates these into a new in-memory
`self._restart_required_outputs: Set[str]` field (cleared by `/api/restart`
alongside the existing `_restart_required` bool), and threads it into
`ui_builder.build_components()` -> `_output_components()`, which now sets
each output `UiComponent.requires_restart` from membership in that set
instead of the previous hardcoded `True`, and `status` to the new
`"restart_required"` value (via `_status_for`'s new parameter) when that's
true and nothing more fundamental (disabled/needs_configuration) overrides
it.

## Context — the constraint that forced it

The existing global `_restart_required` bool and `save_form`'s blanket
`restart_required = bool(outputs) or any(auth.*)` computation had to keep
working exactly as before (Dashboard's "Restart mediainfo" button, the
Overview banner) - this had to be purely additive, not a replacement.
`config.yaml`'s structure and every existing config key's meaning also had
to stay untouched, so persisting "what changed" as new config state was
off the table; it belongs in the same place `_restart_required` itself
already lives - in-memory on `ConfigUiOutput`, reset on restart.

## Alternatives rejected

- **Full before/after value diff of `data["outputs"]` per type** - more
  precise (would correctly no-op a re-save of identical values) but adds
  real risk: ruamel `CommentedMap`/`CommentedSeq` equality semantics under
  `_clean_output_filter_defaults`'s post-merge mutation, deep-copy cost, and
  a subtler bug surface for a first cut whose only consumer today is
  `requires_restart`/`status` (no UI reads it yet - that's task 002).
  Tracking "which type_name was part of this save's `outputs` payload"
  reuses logic that's already there (the existing per-type merge loop) and
  is trivially provable equivalent to the current blanket bool, just
  decomposed by type instead of collapsed to one flag.
- **Persist changed-output-types in config.yaml** (e.g. under
  `ui_hidden_types`-style top-level key) - rejected outright: this is
  process-restart-scoped ephemeral state, not user config, and the
  constraint explicitly rules out changing config.yaml's structure/meaning
  for this.
- **Have `save_raw`/`restore_backup` diff `outputs` against the previous
  file to narrow their conservative "mark everything" fallback** - rejected
  for this task: same equality-semantics risk as above, and both routes
  already carry a documented "safest to assume a restart might be needed"
  precedent for the *global* flag; extending that same conservatism
  per-output keeps the two paths' reasoning consistent rather than having
  raw/restore suddenly behave more precisely than the guided form for no
  strong reason.

## Consequences — what future work is committed to, plus any never-touch warning

- Task 002 (per-card badge) and 003 (Help tab copy) can read
  `UiComponent.requires_restart`/`status == "restart_required"` directly -
  no further backend plumbing needed.
- `_status_for`'s new `restart_required` parameter defaults to `False` and
  is only ever passed `True` from `_output_components` today; if a future
  task wants restart-required status on a non-output component, it needs
  its own truth source (nothing else calls `_status_for` with it yet).
- The subset of `outputs` param keys that aren't registered
  `OUTPUT_CONFIG_TYPES` names were previously still counted toward the
  blanket `restart_required` bool (`bool(outputs)` was true even for an
  all-unknown-type payload); now `changed_output_types` (and therefore
  `restart_required`) only counts keys that were actually known and merged.
  This is a real, deliberate narrowing of an edge case no test exercises
  (the real client never posts an unrecognized output type) - flagged here
  rather than silently shipped.
- Never persist `_restart_required_outputs` to disk without revisiting this
  doc - it is deliberately process-lifetime state, matching
  `_restart_required` itself.

## Findings

Truth-grounding check against the task prompt: everything in
`<background>`/`<context>` matched the code as found (single global
`_restart_required` flag in `output.py`, `save_form`/`save_raw`/
`restore_backup` computing one blanket bool in `config_store.py`,
`_output_components()` hardcoding `requires_restart=True`, and
`ui_model.py`'s `UiStatus` comment reserving `restart_required` as
"not yet derivable... only tracked globally"). No discrepancies found; no
correction needed to the roadmap entry beyond what's recorded above.
