title: Curated "commonly used" markers plus enabled-first sort for Media/Metadata/Displays cards
date: 2026-07-26

## Decision — the choice, named, in one paragraph

Added a static, hand-curated `common: bool` field to `UiComponent` (`ui_model.py`), set in `ui_builder.py` from small per-family frozensets (`_COMMON_SOURCE_TYPES`, `_COMMON_ENRICHER_TYPES`, `_COMMON_OUTPUT_TYPES`) rather than derived from any usage signal, since none exists. `components.js`'s card grids (`sortCardsByRelevance()`) sort on two independent, combined ranks — `enabled` first, then `common` — so an already-configured plugin always stays on top (the returning-user case) while a fresh, nothing-configured-yet install still surfaces likely-relevant plugins first (the case the roadmap entry's `why` names). A small outlined "Popular" badge (`componentCard()`'s `popularBadge`) only renders when a card is common *and not* enabled, since an enabled card already has its own status badge making it self-evidently relevant — the badge would be redundant noise there.

## Context — the constraint that forced it

The roadmap entry's `why`: 18 sources / 19 enrichers / 15 outputs render as one flat, unsorted, unbadged list, so a brand-new install (nothing configured) looks equally overwhelming regardless of what the household actually needs. A configured-first sort alone doesn't help a fresh install (nothing is configured yet); a static curation alone doesn't respect a returning user's own choices. Both were needed together.

## Alternatives rejected

- **Configured-first sort only, no static curation** — rejected: does nothing for the fresh-install case the entry's `why` is actually about (zero components are enabled yet, so the sort would be a no-op there).
- **Static curation only, no enabled-first** — rejected: would let a niche-but-configured plugin rank below an unconfigured "common" one, actively demoting what the household is already using.
- **Derive "commonly used" from some usage/popularity signal** — rejected: no such data exists anywhere in this codebase (no telemetry, no install counts); inventing one would be a much larger, unjustified feature for a UI-ordering nicety.
- **Always show the "Popular" badge on common cards, even enabled ones** — rejected: an enabled card already carries a status badge (Connected/Enabled/etc.) that makes its relevance obvious; a second badge there is visual noise, not information.
- **Reuse a status-colored badge class (`b-connected` etc.) for "Popular"** — rejected: those colors mean ok/warn/error; "Popular" is a curation hint, not a health signal, so it borrows the Activity badges' existing outlined/muted treatment instead (see `dashboard.css`'s `.badge.a-*` precedent).

## Consequences — what future work is committed to, plus any never-touch warning

- The four curated sets are hand-maintained, static judgment calls with no self-correcting mechanism — if they age poorly (a "common" plugin becomes niche, or vice versa) someone has to notice and edit `ui_builder.py` by hand. Revisit periodically rather than assuming it stays accurate.
- `sortCardsByRelevance()` is applied to every `CATEGORY_GROUPS` group in `renderCategorySection()`, including idle_source/theme groups that currently have no `common` markers set — harmless (falls back to enabled-then-alphabetical there), but a future family that wants its own curation should add a set and wire it through the same `common_types` parameter on `_registry_components()`, not invent a second mechanism.
- `common` is deliberately independent of `enabled`/`status` — never conflate them; a future change to status ranking (`_status_for()`) should not assume `common` needs updating in lockstep, and vice versa.

## Findings

Truth-grounding check: `componentCard()`, `renderCategorySection()`, `cardTile()`, and `ui_builder.py`'s `_registry_components()`/`_output_components()`/`build_components()` all matched the code as found — no discrepancies from the entry's stated `touches`. Verified visually with a real browser (Playwright, isolated instance) against the Media and Displays pages: curated sources sort first with a "Popular" badge when disabled, and an enabled common output (`web`, `folder`) correctly shows no redundant badge.
