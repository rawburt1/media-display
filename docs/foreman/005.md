## Decision — the choice, named, in one paragraph

Pipeline and History stop being top-level `#nav` sections and become
sub-views reached through the hash's existing second segment - the same
mechanism `#component/<id>` and `#library/artist/<id>` already use -
selected by a small chip-style sub-nav (`dashboardSubnavHtml()` /
`librarySubnavHtml()`, built on the existing `.filters`/`.chip` CSS this
shell already uses for its card-grid filter bars) rendered at the top of
the shared section: `#dashboard/pipeline` renders Pipeline's stage cards
and priority reordering into `#section-dashboard` (the now-removed
`#section-pipeline` is gone), and `#library/history` renders History's
browse list into `#section-library` (the now-removed `#section-history`
is gone). Help keeps its own hash-addressable `#section-help` and `#help`
route unchanged, but its nav trigger moves out of `#nav` into the sidebar
footer next to Theme/Hitster-safe (`#help-nav-btn`), the cheapest of the
eleven original top-level items to demote since it's a fully static
reference page with no poll-tick fetch of its own. `#pipeline` and
`#history` bookmarks/in-app links still work via a small
`LEGACY_SECTION_ALIASES` table in `parseHash()` that redirects them to
their new nested location instead of falling through to the Dashboard
default like any other unrecognized hash segment would.

## Context — the constraint that forced it

H5 (see `docs/adr/0001-config-ui-two-shell-migration-and-request-lifecycle.md`)
unified this shell's nav specifically so users wouldn't lose their mental
map; History (Fas 9) and Help (this session, before this task) pushed the
sidebar back up to 11 top-level items, re-fragmenting exactly what H5
fixed. Both Pipeline's priority drag-and-drop (its own save/discard flow
sharing `hasUnsavedComponentEdits`) and History's browse list (poll-driven
via the 15s `setInterval`, `/api/history` + per-entry thumbnails) had to
keep working identically, just one level deeper - no backend route, API
shape, or Python code could change.

## Alternatives rejected

- **A new tabs/segmented-control component** - rejected: this shell has no
  existing tab pattern to match (grepped `dashboard.css` for `tab`/`subnav`/
  `segmented` - nothing), and the task rules explicitly ask to reuse an
  existing interaction language rather than introduce a new one. The
  `.chip` row already used for card-grid filters (`filterBarHtml()`) already
  encodes "pick one of several, highlight the active one" - reusing it via
  plain `<a href="#...">` chips (not the filter bar's `<button onclick>`
  chips) also gets the existing `#main` delegated `confirmDiscardIfDirty()`
  click guard for free, the same guard every other in-shell hash link in
  this codebase already relies on.
- **Flatten Pipeline/History permanently into Dashboard/Library as always-
  visible stacked cards** (matching how Library already stacks Browse/
  Overrides/Settings) - rejected: the task explicitly asks for content
  reachable "one level deeper," not merged flat and always rendered/
  fetched; an always-visible Pipeline would mean fetching
  `/api/ui/pipelines` and priority lists on every Dashboard visit and poll
  tick regardless of whether the user is looking at them, which the
  original top-level Pipeline section never did either.
- **Keep Help as a top-level `#nav` button** - rejected: named in the task
  prompt itself as "the cheapest candidate here to demote," fully static
  (no fetch beyond data Dashboard already loaded), and moving it further
  reduces the top-level count (8 buttons in `#nav` now, down from 11)
  without losing any functionality - it keeps its own hash route and
  section, just a different nav trigger location.
- **Silently let old `#pipeline`/`#history` hashes fall through to the
  Dashboard default** (parseHash()'s normal behavior for any unrecognized
  head segment) - rejected per the task's explicit deep-linkability
  requirement: an old bookmark or in-app link should land where the user
  expects, not silently redirect to a different page than the one it
  named.

## Consequences — what future work is committed to, plus any never-touch warning

- Any future in-shell link to Pipeline or History must use
  `#dashboard/pipeline` / `#library/history`, not a bare `#pipeline` /
  `#history` (the latter still works via `LEGACY_SECTION_ALIASES`, but is
  now a compatibility shim, not the canonical route - grepped the whole
  repo for `#pipeline`/`#history` before this change and found no other
  reference outside `dashboard.js`/`dashboard.html`/`components.js`
  themselves, so no other template/doc needed updating).
- `renderPipeline()` now writes into `#section-dashboard` (not a
  dedicated element) and `renderHistorySection()` was removed entirely -
  its old body was folded into `renderLibrarySection()`'s `param ===
  'history'` branch. Anything that assumed either function's old target
  element (`#section-pipeline`/`#section-history`) is stale.
- `currentSection` alone no longer identifies Pipeline/History - callers
  (the poll `setInterval`, `fetchPipeline()`, `fetchComponents()`,
  `fetchHistory()`) must check `currentSection === 'dashboard' &&
  currentParam === 'pipeline'` / `currentSection === 'library' &&
  currentParam === 'history'` instead of a dedicated `currentSection`
  value. A future section nested the same way should follow this same
  `section + param` pairing rather than inventing a third convention.
- `subnavChips()` (dashboard.js) is now shared infrastructure - a third
  nested sub-view should reuse it rather than duplicating chip-row markup.
- Never restyle `.chip` to assume it's always inside the filter bar's
  `<button onclick>` context - it's now also used as a plain `<a href>` for
  sub-nav (needed a `text-decoration: none` addition to `.chip` in
  `dashboard.css` to look right as an anchor; any future `.chip` change
  must keep working for both element types).
